## 1. 项目当前形态

两个部分，通过「USB 串口 + Wi-Fi/WS」配合：

- **固件（`firmware/`）**：ESP32-C6-Touch-AMOLED-2.16 板级固件，ESP-IDF 5.5.5。
  负责屏幕 UI（时钟、四个按键、待机页）、板载 PCF85063A RTC、QMI8658 陀螺仪空中鼠标（BLE HID）、
  Wi-Fi 语音会话（板端 16 kHz PCM 经 WSS 上行）、USB 串口配网/调试命令（`AR1*`）。
- **DSH 插件（`plugins/dsh-airremote/`）**：DeepSeek Harness 插件（TypeScript + React）。
  宿主侧把开发板当成**虚拟麦克风**喂给官方语音输入插件；设置页提供「开发板时间」（时区 + 校时）
  与「固件烧录」（宿主进程 esptool-js 直接烧内置镜像）。

配合方式：板子按 `AR1T/AR1Z` 拿到时间与时区；插件通过 UDP 47682 发现、WSS 47683 取 PCM；
烧录与校时都走 **COM7（USB-Serial/JTAG）**，由宿主的串口互斥（`SerialHolder`）保证不同时占用。

## 3. 未完成项与已知问题（按优先级）

### 1) 【P0】待机页只显示冒号，数字全空白（已修复，`8d0f43f`）
- **现象**：待机页只有 `:`，`HH:MM` 的数字不渲染。
- **影响**：待机页核心信息缺失，用户已反馈。
- **根因（已确认，非字体数据问题）**：
  LVGL 9.6 在绘制每个字形前，要把字形位图重采样成 **A8 蒙版**，缓冲按 `LV_ROUND_UP(box_h,32)` 对齐、**从 LVGL 自己的内存池 `lv_malloc` 分配**（`lv_draw_label.c:686-702`）。
  - 数字蒙版：`'0'` 90×128 = **11520 B**、`'4'` 98×128 = 12544 B；冒号只有 18×96 = **1728 B**；
  - 真机日志：`lvgl mem: total=18104 free=5124`，建完待机页 `free=3132 biggest=3132 B`；
  - ⇒ 11520 B ≫ 3132 B → **4 个数字的蒙版分配失败**（`LV_USE_LOG` 关闭，报错被编译掉，静默不画）；冒号 1728 B 能分配，所以只剩冒号。主界面 48px 文字蒙版约 1.7 KB，刚好能过。
  - 字体文件本身健康：cmap 覆盖 `0123456789:` 全部 11 个字形（`:5981`）、`'1'` 位图非零、`line_height=115 / base_line=1` 经公式复算**自洽**（Montserrat 的 hhea ascent=114/-1），**不是元凶**。
- **修复（已实施，`8d0f43f`）**：采用下面的**方案 2**——把字形绘制蒙版改为从系统堆分配
  （commit message：`standby clock glyph buffer on system heap`）。静态 `.bss` 不涨，仅在待机绘制瞬间占 ~11.5 KB。
- **状态：已由 `8d0f43f` 修复**，待机页 `HH:MM` 恢复显示。
  ⚠️ 复盘：这段时间曾把该现象**误判为「旧镜像导致」**，其实**两件事叠加**：① 板子上是旧镜像；
  ② 那台机器的本地树落后 `origin/main` 7 个 commit，**`8d0f43f` 本身就没被同步过去**——
  所以「换镜像」不能单独解决问题，必须**先同步再构建**（见第 6 节事故 3）。
- **历史方案评估（保留备查，勿再按此实施）**：
  1. `CONFIG_LV_MEM_SIZE` 20480 → 30720/32768（`firmware/sdkconfig.defaults`），最直接，但静态 `.bss` +10~12 KB，`heap after ble free` 会从 ~20 KB 掉到 ~8-10 KB，**可能压死 Wi-Fi**；
  2. **推荐**：把字形绘制蒙版改为从系统堆分配（覆盖 `LV_GLOBAL_DEFAULT()->font_draw_buf_handlers`，可用 `lv_draw_buf_get_font_handlers()` 取默认），静态不涨，仅在待机绘制瞬间占 ~11.5 KB；
  3. 放弃 160px 字号（会让数字明显变小，违背已批准布局），不建议。
- **涉及**：`firmware/sdkconfig.defaults`、`firmware/components/app_ui/app_ui.c`；字体文件 `fonts/ui_font_standby_160.c` **不用动**（未改动，确认不是字体数据问题）。

### 2) 【P1】陀螺仪四项待修（用户已批准修改方案）
- **a. 滚转串扰**：`air_mouse.c:46-56` `pitch_axis()` 首选 `cross(gravity, screen_normal)`，滚转时轴偏到前后轴 → 「右侧下压」串出 `dy +1~+7`。建议改用 `unit(perpendicular({1,0,0}, gravity))`。
- **b. 语义抵消**：`air_mouse.c:26` `screen_normal={0,0,1}` 实际 +Z 朝屏背面，与 `:23` `VERTICAL_SIGN=+1` 两个错误正好抵消。改成 `{0,0,-1}` **且** `VERTICAL_SIGN=-1`（必须同改）。
- **c. 退出 Gyro 偶发崩溃**：`busy: hold -gyro` 后 `Guru Meditation (Store access fault)`，当时 BLE 已连接且 HID 正在发；未能稳定复现。需审查 `release_pending`/`mode_generation` 竞态与 `imu` 句柄生命周期。
- **d. 加速度量程**：静止 `accel_mag≈10.47` vs `9.80665`（+6.8%），而校准判据 `fabsf(accel_mag-GRAVITY) > 1.0f` 只剩 ~0.3 余量，手抖易让校准清零重来。需核对 `CTRL2` 量程与库灵敏度换算，或改成按比例容差（如 `0.15f*GRAVITY`）。

### 3) 【P1】语音会话起不来（用户已决定暂不修）
- **现象**：`AR1V` / 点 Voice → `PCM buffer allocation failed`，进不了 AUTH。
- **原因**：`voice.c` `voice_task` 先 `audio_open()` 申请 16 KB 连续块，再 `ble_mouse_release()`；BLE 起来后 8-bit DRAM 已无 16385 字节连续块（有 BLE 连接时 free≈16.6 KB）。顺序与注释矛盾。
- **影响**：语音链路与 Wi-Fi 关联都无法工作（Wi-Fi 只在语音会话里 `connect_wifi()`）。
- **建议改法**：把 `ble_mouse_release()` 挪到 `audio_open()` 之前；或改由 PSRAM/分块缓冲。
- **涉及**：`firmware/components/app_voice/voice.c`。

## 6. 事故与教训

### 事故 1：串口句柄泄漏（已修复，`b3ebadb`）
- `src/host/serial-port.ts` 里 `port.on('data', …)` 写在 `try/finally` **之外**，抛
  `Cannot read properties of undefined (reading '_readableState')` 时端口没有被 `close()`。
- 后果：Windows 独占句柄泄漏，**拔插 USB 两次都没释放**，只有杀掉宿主进程或强行过继句柄
  （`DuplicateHandle(..., DUPLICATE_CLOSE_SOURCE)`）才能恢复。
- 修复：整个生命周期（构造→open→监听→收发→close）纳入同一个 `try/finally`，
  `close()` 1 秒超时后 `destroy()` 兜底。
- **教训**：串口/文件句柄的释放必须写在 `finally` 里，且 `open` 之后的每一行都算在「可能抛异常」范围内。

### 事故 2：烧录取消测试顺序错误，擦掉了 NVS 配网（已恢复凭据）
- 真机验证时先做了「写中取消」测试，**后**才备份 NVS；而 esptool 的 `flashBegin` 是**先擦整段再写**，
  于是 NVS（Wi-Fi 凭据 + tz）在备份之前就被擦空了，原内容不可恢复。
- 处理：用 `netsh` 读本机 WLAN 凭据，`AR1W` 重新写入（`AR1 WIFI OK`），并重设 `AR1T`/`AR1Z 480`。
- **教训**：今后真机测试顺序统一为 **先备份 → 再做破坏性测试 → 最后恢复并验证**；
  任何烧录/擦除/写中取消之前，必须先 `read_flash` 备份 nvs 区间（本板 `0x9000` 起 `0x107000` 字节）。

### 事故 3：在落后 origin 7 个 commit 的本地树上构建并烧录（2026-11-11）

- **现象**：待机页退化成**只显示冒号**（`:`），`HH:MM` 的数字全部空白，用户据此排查了一轮。
- **根因**：当天开工**没有先 `pull`**，本地 `main` 落后 `origin/main` **7 个 commit**；
  构建和烧录都基于这棵旧树，板子里的镜像**根本不含** `8d0f43f`
  （`standby clock glyph buffer on system heap`，即待机页数字的修复）。
- **误判过程**：期间曾把现象归因为「旧镜像导致」。方向只对了一半——**换镜像也没用**，
  因为那台机器的树里根本没有这个修复；实际是**旧镜像 + 修复未同步**两件事叠加。
- **教训**：**开工先同步**（`fetch` + `pull --ff-only origin main`）；
  **构建前确认 `git rev-list --count origin/main..HEAD` 为 0**，非 0 一律不构建、不烧录、不改代码。
- **处理**：
  ```powershell
  git diff > standby-glyph-$(Get-Date -Format yyyyMMdd-HHmmss).patch   # 先把本地改动存 patch
  git checkout -- firmware/                                            # 回到干净树（需要时再 git apply 回来）
  git -c http.proxy=http://127.0.0.1:7897 pull --ff-only origin main    # 同步到含 8d0f43f 的 main
  # 然后重新构建 → 重新烧录 → 真机确认待机页 HH:MM 正常
  ```
- **结果**：同步后重建重烧，待机页 `HH:MM` 恢复正常显示。
