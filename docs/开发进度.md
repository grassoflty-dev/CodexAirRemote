## 1. 项目当前形态

两个部分，通过「USB 串口 + Wi-Fi/WS」配合：

- **固件（`firmware/`）**：ESP32-C6-Touch-AMOLED-2.16 板级固件，ESP-IDF 5.5.5。
  负责屏幕 UI（时钟、四个按键、待机页）、板载 PCF85063A RTC、QMI8658 陀螺仪空中鼠标（BLE HID）、
  Wi-Fi 语音会话（板端 16 kHz PCM 经 WSS 上行）、USB 串口配网/调试命令（`AR1*`）。
- **DSH 插件（`plugins/dsh-airremote/`）**：DeepSeek Harness 插件（TypeScript + React）。
  宿主侧把开发板当成**虚拟麦克风**喂给官方语音输入插件；设置页提供「开发板时间」（时区 + 校时）
  与「固件烧录」（宿主进程 esptool-js 直接烧内置镜像）。

配合方式：板子按 `AR1T/AR1Z` 拿到时间与时区；插件通过 UDP 47682 发现、WSS 47683 取 PCM；
烧录与校时走 **USB-Serial/JTAG**（端口**不写死**：按 USB VID `303A` 自动识别，可用 `AIRREMOTE_SERIAL_PORT` 或 `-p` 指定），由宿主的串口互斥（`SerialHolder`）保证不同时占用。

## 2c. 旋转功能闭环（2026-11-13，用户目视确认）

上一版旋转是「flush 回调里逐像素软件转置」，每帧要一块 11.5 KB 的 DMA scratch —— BLE 起来后这块内存根本拿不到，
于是按一次 ROTATE 就整机冻结（见第 6 节事故 5）。现在改成面板自己转：方向由 SH8601 的 `0x36` MADCTL 决定，
CPU 不再搬像素，也不占任何 scratch。

`0x36` 以 `0x30` 为基线，只改 MY/MX/MV 三位，四个方向就这四个值：

| 方向 | `0x36` 值 |
|---|---|
| 0° | `0x30` |
| 90° | `0x50` |
| 180° | `0xF0` |
| 270° | `0x90` |

验收基线如下，后续改动不得回退：

| 项目 | 口径 | 结果 |
|---|---|---|
| 旋转方式 | MADCTL 硬件旋转，**每次 init 之后必须补发一次 `0x36`**（init 序列会把它覆盖掉，否则只有首个方向不生效，方向键按了没反应） | ✅ |
| 触摸 | LVGL 用 `lv_display_rotate_point()` 自行反变换，read_cb 不再手写坐标转换 | ✅ |
| 切换时机 | 按钮只置 `pending_rotation`，20 ms `lv_timer` 等到 `disp->flushing==0` 才动手：「写 MADCTL → `lv_display_set_rotation()` → 整屏 invalidate」，避免在 flush 中途改方向 | ✅ |
| 卡死兜底 | `lv_display_set_flush_wait_cb()` 100 ms 超时：单次颜色传输失败只丢帧 + 报错，不再永久卡死 | ✅ 压测 flush 超时 0 |
| 画面方向 | 0°/90°/180°/270° 四个方向用户**目视确认**正确 | ✅ |
| 鼠标方向 | 旋转后 HID 空中鼠标方向正确（屏幕旋转不改 HID 轴映射的约定不变） | ✅ |
| 压测 | 80 次按压 / 72 次四向切换（18 轮 90→180→270→0），并发拖亮度、开/关设置页、进/出待机 | ✅ panic 0 / flush 超时 0 / alloc failed 0 / 白屏 0 |
| 整屏覆盖 | 四个方向的 band 数 `44/43/44/46`，每块都覆盖 `x=0..479`，无缺块 | ✅ |

涉及 commit：`bc29851`（MADCTL 替换软件转置）、`465f6fe`（圆角 mask 分配失败导致的崩溃修复）。

## 2d. 回归红线（内存基线，2026-11-13 起执行）

这两条数字是旋转收口时的真实实测值，以后改 UI、改 LVGL 配置、动 BLE 相关路径，都拿它们当红线比对；
明显变差就先查清原因再继续，不要「先烧上去看看」。

| 指标 | 红线 | 说明 |
|---|---|---|
| BLE 起来后 internal free | **13528 B** | 连上 BLE 之后系统内部堆的可用量，低于它 Wi-Fi / 语音这类大块申请基本没戏 |
| LVGL 池历史最小 | **free 4432 B / biggest 3288 B** | 建完待机页并跑完旋转压测期间出现过的最低水位 |

对照：改前基线是 internal free **17136 B**、LVGL total **20152 B**。现在 `LV_MEM_SIZE` 是 25600 B（+3 KiB），
所以 **LVGL total 变大是预期**，要看的是 free / biggest 的**最小值**，不是总量。

## 3. 未完成项与已知问题（按优先级）

### 1) 【P0】待机页只显示冒号，数字全空白（已修复，`8d0f43f`）
- **现象**：待机页只有 `:`，`HH:MM` 的数字不渲染。
- **影响**：待机页核心信息缺失，用户已反馈。
- **根因（已确认，非字体数据问题）**：
  LVGL 9.6 在绘制每个字形前，要把字形位图重采样成 **A8 蒙版**，缓冲按 `LV_ROUND_UP(box_h,32)` 对齐、**从 LVGL 自己的内存池 `lv_malloc` 分配**（`lv_draw_label.c:686-702`）。
  - 数字蒙版：`'0'` 90×128 = **11520 B**、`'4'` 98×128 = 12544 B；冒号只有 18×96 = **1728 B**；
  - 真机日志：`lvgl mem: total=18104 free=5124`，建完待机页 `free=3132 biggest=3132 B`；
  - ⇒ 11520 B ≫ 3132 B → **4 个数字的蒙版分配失败**（`LV_USE_LOG` 关闭，报错被编译掉，静默不画）；冒号 1728 B 能分配，所以只剩冒号。主界面 48px 文字蒙版约 1.7 KB，刚好能过。
  - 字体文件本身健康：cmap 覆盖 `0123456789:` 全部 11 个字形（`:5981`）、`'1'` 位图非零、`line_height=115 / base_line=1` 经公式复算**自洽**（Montserrat 的 hhea ascent=114/-1），**不是元凶**。
- **修复（已实施，`8d0f43f`）**：采用下面的**方案 2**——把字形绘制蒙版改为从系统堆分配
  （commit message：`standby clock glyph buffer on system heap`）。静态 `.bss` 不涨，仅在待机绘制瞬间占 ~11.5 KB。
- **状态：已由 `8d0f43f` 修复**，待机页 `HH:MM` 恢复显示。
  ⚠️ 复盘：这段时间曾把该现象**误判为「旧镜像导致」**，其实**两件事叠加**：① 板子上是旧镜像；
  ② 那台机器的本地树落后 `origin/main` 7 个 commit，**`8d0f43f` 本身就没被同步过去**——
  所以「换镜像」不能单独解决问题，必须**先同步再构建**（见第 6 节事故 3）。
- **历史方案评估（保留备查，勿再按此实施）**：
  1. `CONFIG_LV_MEM_SIZE` 20480 → 30720/32768（`firmware/sdkconfig.defaults`），最直接，但静态 `.bss` +10~12 KB，`heap after ble free` 会从 ~20 KB 掉到 ~8-10 KB，**可能压死 Wi-Fi**；
  2. **推荐**：把字形绘制蒙版改为从系统堆分配（覆盖 `LV_GLOBAL_DEFAULT()->font_draw_buf_handlers`，可用 `lv_draw_buf_get_font_handlers()` 取默认），静态不涨，仅在待机绘制瞬间占 ~11.5 KB；
  3. 放弃 160px 字号（会让数字明显变小，违背已批准布局），不建议。
- **涉及**：`firmware/sdkconfig.defaults`、`firmware/components/app_ui/app_ui.c`；字体文件 `fonts/ui_font_standby_160.c` **不用动**（未改动，确认不是字体数据问题）。

### 2) 【P1】陀螺仪四项待修（用户已批准修改方案）
- **a. 滚转串扰**：`air_mouse.c:46-56` `pitch_axis()` 首选 `cross(gravity, screen_normal)`，滚转时轴偏到前后轴 → 「右侧下压」串出 `dy +1~+7`。建议改用 `unit(perpendicular({1,0,0}, gravity))`。
- **b. 语义抵消**：`air_mouse.c:26` `screen_normal={0,0,1}` 实际 +Z 朝屏背面，与 `:23` `VERTICAL_SIGN=+1` 两个错误正好抵消。改成 `{0,0,-1}` **且** `VERTICAL_SIGN=-1`（必须同改）。
- **c. 退出 Gyro 偶发崩溃**：`busy: hold -gyro` 后 `Guru Meditation (Store access fault)`，当时 BLE 已连接且 HID 正在发；未能稳定复现。需审查 `release_pending`/`mode_generation` 竞态与 `imu` 句柄生命周期。
- **d. 加速度量程**：静止 `accel_mag≈10.47` vs `9.80665`（+6.8%），而校准判据 `fabsf(accel_mag-GRAVITY) > 1.0f` 只剩 ~0.3 余量，手抖易让校准清零重来。需核对 `CTRL2` 量程与库灵敏度换算，或改成按比例容差（如 `0.15f*GRAVITY`）。

### 3) 【已修复，`67791e3`】待机页数字整格不画（比"只剩冒号"更深一层）
- **现象**：先是 `14:25` 显示成 `1 :25`（只有 '4' 消失），随后 `08:08` 变成小时两位
  全空白；分钟 `15` 一直正常。占位还在、像素没有。
- **根因（真机日志证据，非推测）**：LVGL 9.6 给每个字形现算 A8 蒙版，
  `'0'`=90×128=**11520 B**、`'8'`=11264、`'9'`=11008、`'4'`=98×128=**12544**；
  而 BLE 连接后系统堆只有 `free 15496 / largest 10752`，超过 10752 的蒙版**分配失败
  就整格不画**（`LV_USE_LOG` 关闭时静默）。`'1'`=4992、`'5'`=10496 能过 —— 与
  "只缺 '0'/'4'/'8'"完全一致。
- **两层失败的区分**：第一层是 100 px 格子 < advance(106 px) 被默认 WRAP 换到第二行
  裁掉（`1 :25`）；第二层才是上面的蒙版分配失败（`08:08` 整小时空白）。
- **修复**：160 px 的 11 个字形在构建期导成 **A8 位图资源**（`fonts/standby_glyphs.c`，
  94 KB flash、0 堆；生成脚本 `firmware/tools/gen_standby_glyphs.py`），待机页用
  `lv_image` 显示，位置按字体度量算，运行时不分配任何内存。
- **第二轮修正（字形数据，真机表现为 `'1'` 画成三条斜线）**：两个坑都出在转换脚本，不在 LVGL：
  1. **A8 的 stride 必须是 `box_w`（无行填充）**。我第一版按 4 字节对齐填了 padding
     （`'1'` 为 40 而实际宽 39），LVGL 画 A8 时按宽度取行，padding 让每行错位 1 字节、
     逐行累积 → 斜线。现在 `header.stride == box_w` 是不变量。
  2. **字体 4bpp 是"行连续打包"**（`lv_font_fmt_txt_dsc_t.stride == 0`），位偏移是
     `(y*box_w + x)*4`，不是 `ceil(box_w/2)` 逐行对齐。偶数宽字形（`'0'` 90、`'4'` 98…）
     恰好字节对齐所以没暴露，奇数宽（`'1'` 39、`'2'`/`'7'` 83、`'6'` 85）会错位。
- **自检再升级（这次真的能证明"画的是对的字"）**：开机时把每个 A8 资源与字体原始 4bpp
  数据**逐像素比对**（固件内独立实现，不走生成脚本），并校验 `stride == box_w`；
  真机日志 `standby: glyphs vs font '0':0/10260 '1':0/4407 … ':':0/1548`，任何差异打
  `E GLYPH MISMATCH`。**墨量比例不能当判据**（`'1'` 的 39.8% 是它 39 px 窄框的正常值）。
- **教训（自检必须覆盖三条）**：只看 `wrapped`/坐标查不出"蒙版分配失败"这种绘制期
  故障，所以现在每秒日志同时打印 `layout=ok/ERROR`（每格图片已设置、尺寸=字形度量、
  坐标在 0..479 内）、`glyphs=1`（开机逐个字形校验非零像素）、`mask_fail=0`
  （字形蒙版分配失败计数），任一异常打 `E STANDBY LAYOUT ERROR`。

### 3b) 【已修复，`未提交前`】待机页真实触摸唤不醒（调试钩子把这个问题掩盖了）
- **现象**：进待机后用手指触摸无法回到主界面（第三键能唤醒，说明主循环没卡）。
- **根因**：唤醒写在 `app_ui.c` 的 `touch_pressed()`（indev 的 `LV_EVENT_PRESSED` 回调）里，
  该回调在 **LVGL 输入派发过程中**直接 `leave_standby()`：隐藏待机页、并把电量标签
  `lv_obj_set_parent` 挂回主屏幕 —— 在派发过程中改对象树，导致唤醒异常/点了没反应。
- **为什么自检没抓到**：以前用 `AR1S TAP`（`lv_indev_send_event` 直接注入事件）验证，
  它**绕过真实 indev 读取路径**，两条路径不同，所以"自检全绿但用户摸不醒"。
  **结论：凡是输入相关的验证，一律用真实触摸/按键，日志必须能区分（见下）。**
- **修法**：indev 回调只置位 `standby_wake_request`，切页在 `render()` 的 LVGL 循环里做
  （与第三键同一套模型）；每次真实触摸打 `ui: real touch #N, standby=<0|1>`，
  每秒待机日志加 `touches=N wakes=M`，从此**能区分真实触摸与 `AR1S TAP` 注入**。
- **顺带**：RTC 时间无效时待机页不再显示 `00:00` 假数据（大数字隐藏、秒行 `--`）；
  `rtc_board_init()` 每次开机打印 `control_1` 的 STOP 与 `seconds` 的 OS 位，便于判定断电。
- **无效时间判据与验证（真机做过）**：判据是 **年 < 2024 即无效**（`RTC_MIN_YEAR 2024`）、
  另外 `current_utc()` 要求 `>= 2024-01-01`。PCF85063 掉电复位到 2000-01-01 属"结构合法"，
  旧判据（只查 2000）会放过，现在会被判无效。验证方式：临时探针把 RTC 寄存器写成
  `2000-01-01 00:00:00` → 真机日志 `standby: clock invalid, placeholder shown`，屏上大数字
  隐藏、秒行显示 `--`；探针用完即删。
- **`AR1T` 写时路径自查**：`rtc_board_set_unix()` 只写 0x04..0x0A 时间寄存器，**从不碰
  `control_1`（STOP）**；写完会回读并打印 `RTC readback … control_1=0x01 (STOP=0),
  seconds=0xNN (OS=0)`，真机已验证写进去且振荡器没停。

## 6. 事故与教训

### 事故 1：串口句柄泄漏（已修复，`b3ebadb`）
- `src/host/serial-port.ts` 里 `port.on('data', …)` 写在 `try/finally` **之外**，抛
  `Cannot read properties of undefined (reading '_readableState')` 时端口没有被 `close()`。
- 后果：Windows 独占句柄泄漏，**拔插 USB 两次都没释放**，只有杀掉宿主进程或强行过继句柄
  （`DuplicateHandle(..., DUPLICATE_CLOSE_SOURCE)`）才能恢复。
- 修复：整个生命周期（构造→open→监听→收发→close）纳入同一个 `try/finally`，
  `close()` 1 秒超时后 `destroy()` 兜底。
- **教训**：串口/文件句柄的释放必须写在 `finally` 里，且 `open` 之后的每一行都算在「可能抛异常」范围内。

### 事故 2：烧录取消测试顺序错误，擦掉了 NVS 配网（已恢复凭据）
- 真机验证时先做了「写中取消」测试，**后**才备份 NVS；而 esptool 的 `flashBegin` 是**先擦整段再写**，
  于是 NVS（Wi-Fi 凭据 + tz）在备份之前就被擦空了，原内容不可恢复。
- 处理：用 `netsh` 读本机 WLAN 凭据，`AR1W` 重新写入（`AR1 WIFI OK`），并重设 `AR1T`/`AR1Z 480`。
- **教训**：今后真机测试顺序统一为 **先备份 → 再做破坏性测试 → 最后恢复并验证**；
  任何烧录/擦除/写中取消之前，必须先 `read_flash` 备份 nvs 区间（本板 `0x9000` 起 `0x107000` 字节）。

### 事故 3：在落后 origin 7 个 commit 的本地树上构建并烧录（2026-11-11）

- **现象**：待机页退化成**只显示冒号**（`:`），`HH:MM` 的数字全部空白，用户据此排查了一轮。
- **根因**：当天开工**没有先 `pull`**，本地 `main` 落后 `origin/main` **7 个 commit**；
  构建和烧录都基于这棵旧树，板子里的镜像**根本不含** `8d0f43f`
  （`standby clock glyph buffer on system heap`，即待机页数字的修复）。
- **误判过程**：期间曾把现象归因为「旧镜像导致」。方向只对了一半——**换镜像也没用**，
  因为那台机器的树里根本没有这个修复；实际是**旧镜像 + 修复未同步**两件事叠加。
- **教训**：**开工先同步**（`fetch` + `pull --ff-only origin main`）；
  **构建前确认 `git rev-list --count origin/main..HEAD` 为 0**，非 0 一律不构建、不烧录、不改代码。
- **处理**：
  ```powershell
  git diff > standby-glyph-$(Get-Date -Format yyyyMMdd-HHmmss).patch   # 先把本地改动存 patch
  git checkout -- firmware/                                            # 回到干净树（需要时再 git apply 回来）
  git -c http.proxy=http://127.0.0.1:7897 pull --ff-only origin main    # 同步到含 8d0f43f 的 main
  # 然后重新构建 → 重新烧录 → 真机确认待机页 HH:MM 正常
  ```
- **结果**：同步后重建重烧，待机页 `HH:MM` 恢复正常显示。


### 事故 4：待机字形资源 stride / 4bpp 解码错误（`'1'` 画成三条斜线，`d879923`）

- **现象**：`1` 不显示或显示成斜线；而 `layout=ok / glyphs=1 / mask_fail=0 / ink>0` 四条自检全绿。
- **根因（两处叠加，都在生成脚本）**：
  1. **A8 资源的 stride 必须等于 `box_w`（无行填充）**。第一版按 4 字节对齐填 padding（`'1'` 40 vs 宽 39），
     LVGL 画 A8 按宽度取行，padding 让每行错位 1 字节、逐行累积 → 斜线。
  2. **字体 4bpp 的行是连续打包**（`lv_font_fmt_txt_dsc_t.stride == 0`），像素位偏移是
     `(y*box_w + x)*4`，**不是** `ceil(box_w/2)` 逐行对齐。偶数宽字形（`'0'` 90、`'4'` 98…）恰好字节对齐
     所以没暴露；奇数宽（`'1'` 39、`'2'`/`'7'` 83、`'6'` 85）会错位。两者错一个就出斜线。
- **自检升级**：开机把每个 A8 资源与字体原始 4bpp 数据**逐像素比对**（固件内独立实现），并校验
  `stride == box_w`；任何差异打 `E GLYPH MISMATCH`。真机日志
  `standby: glyphs vs font '0':0/10260 '1':0/4407 … ':':0/1548`（全部 0 差异）。
- **教训**：**"有墨"不等于"画的是对的字"**；位图资源必须有"与源数据逐字节等价"的自检，墨量比例不能当判据
  （`'1'` 的 39.8% 是其 39 px 窄框的正常值）。

### 事故 5：旋转卡死（0.6.1 软件转置版）

- **现象**：按一下 ROTATE，屏幕冻结、整机卡死，连 `AR1?` 都不回；5 秒起 `task_wdt: CPU 0: lvgl` **无限刷屏但不重启**
  （`CONFIG_ESP_TASK_WDT_PANIC` 没开，所以看门狗也救不回来）。
- **根因**：flush 内软件转置要一块 11.5 KB 的 **DMA** scratch。BLE 起来后 DMA 池只剩 `free 4932 / largest 3520`，
  DMA 分配失败后退回 non-DMA，SPI 驱动自己的私有 DMA 反弹缓冲也分配失败
  （`setup_dma_priv_buffer: Failed to allocate priv TX buffer`）→ `panel_io_spi_tx_color` 失败 →
  `flush_ready` 永不回调 → LVGL 单缓冲在 `while (disp->flushing)` 里自旋，整个显示任务就焊死在那里。
- **教训**：**LVGL 默认的 flush 等待就是自旋**（官方文档明说），任何一次颜色传输失败都会升级成整机冻结，
  而不是"这一帧没画出来"。所以 `lv_display_set_flush_wait_cb()` 的超时兜底不是可选项，是必需品。
- **修法**：放弃软件转置，改用 MADCTL 硬件旋转（`bc29851`），scratch 需求直接归零；同时补上 100 ms flush 超时兜底。

### 事故 6：旋转崩溃（MADCTL 首版，`465f6fe` 修复）

- **现象**：旋转后画面先割裂，接着白屏，然后自动重启回到主界面。
- **根因**：旋转要求整屏重绘，而 LVGL 池当时只有 22528 B，峰值只剩 `free=440 / biggest=280`。
  圆角控件的 AA mask 需要 `(半径+1)*16` 字节（亮度旋钮 r=22 → 368 B），`lv_draw_sw_mask.c:1060` 分配失败；
  LVGL 9.6 在这里把 circle 缓存留成了**毒化状态**——`radius` 已写入、指针却是 NULL。
  下一帧同半径的圆角再来命中毒化项，读 `c->opa_start_on_y` 时 `MTVAL=0x8` 空指针 → `Load access fault` panic。
- **修法**（三条一起上）：
  1. `LV_MEM_SIZE` 22528 → **25600**（+3 KiB），把峰值余量拉开；
  2. `LV_DRAW_SW_CIRCLE_CACHE_SIZE` **4 → 8**：本工程一共 6 种圆角半径（7/17/18/19/20/22），
     缓存能全部装下 → 全程命中、零分配 → **毒化那条路径根本走不到**，这才是治本；
  3. 延迟切换加固（`disp->flushing==0` 才换方向），避免在渲染中途改显示参数。
- **教训**：**"扩容"只是留余量，"让缓存命中"才是治本**。以后再新增一种圆角半径，必须回头复查
  `LV_DRAW_SW_CIRCLE_CACHE_SIZE` 够不够装；否则圆角一多，同样会在内存最紧张的那一帧炸掉。

用户说的「第三个键」= **既不是 BOOT、也不是电源键** 的那个实体按键，官方资料称 **KEY 按键**。

### 官方资料

  「板载 KEY、BOOT 两个可自定义功能的侧边按钮」；按键说明节有 `BOOT 按键` / `PWR 电源按键` / `KEY 按键`。
- 原理图 `ESP32-C6-Touch-AMOLED-2.16-Schematic.pdf`（wiki 附件
  <https://www.waveshare.net/w/upload/4/47/ESP32-C6-Touch-AMOLED-2.16-Schematic.pdf>）网络表：
  - `PIC1402PIKey102PIR801PIU2015NLGPIO9` → **Key1**（BOOT）接 **GPIO9**，R8 10K 上拉、C14；
  - `PIC2202PIKey302PIR1801PIU2016NLGPIO10` → **Key3**（KEY）接 **GPIO10**，R18 10K 上拉、C22 标 `NC/100nF`（未贴）；
  - 同页引脚表 `GPIO915GPIO1016GPIO1117…`（GPIO9=pin15、GPIO10=pin16）与上面 U2-15/U2-16 互证；
  - 官方 XiaoZhi 板级配置 `02_Example/XiaoZhi-v2.2.5/main/boards/waveshare/esp32-c6-touch-amoled-2.16/config.h`
    里只有 `#define BOOT_BUTTON_GPIO GPIO_NUM_9`，没有第二路按键。
- 结论：**板子只有 BOOT / PWR / KEY 三个物理键，没有独立 RST 键**（CHIP_PU 由 BSS138 自动下载电路驱动），
  所以第三键**可以**用来做「短按进待机」。

### 实测（临时探针，GPIO9/GPIO10/GPIO6 配成上拉输入，5 ms 轮询）
```
I (2205) probe BOOT gpio 9, idle level 1
I (2205) probe KEY gpio 10, idle level 1
I (2206) probe SD_CS gpio 6, idle level 1
I (351029) probe BOOT gpio 9 -> 0, bounce edges 0 in 40 ms
I (352260) probe KEY gpio 10 -> 0, bounce edges 0 in 40 ms     <-- 第三键按下
I (352450) probe KEY gpio 10 -> 1, bounce edges 0 in 40 ms     <-- 松开
I (355390) probe KEY gpio 10 -> 0, bounce edges 0 in 40 ms
I (356240) probe KEY gpio 10 -> 1, bounce edges 0 in 40 ms
```
判据：**GPIO10、按下为低（空闲高）、40 ms 内抖动 0 次、与现有外设无冲突**

软件仍需消抖（C22 未贴），`app_key` 用 25 ms。

### 0.6.0 真机事故（已修复，务必别再踩）

为了让「万一显示改成 DIRECT 模式」也能旋转，0.6.0 打开了
`CONFIG_LV_USE_MATRIX=y` + `CONFIG_LV_DRAW_TRANSFORM_USE_MATRIX=y`。
后果：LVGL 绘制改走 draw layer（`CONFIG_LV_DRAW_LAYER_SIMPLE_BUF_SIZE=24576`），
20 KiB 的 LVGL 池在建完待机页后**只剩 88 B**，下一帧渲染即崩溃：

```
I (2162) air_remote: lvgl mem +standby page: free=88 biggest=76 delta=4888 B
Guru Meditation Error: Core 0 panic'ed (Store access fault)
0x420a9b32: lv_draw_add_task  .../src/draw/lv_draw.c:100     (addr2line)
```

→ `Store access fault` → `rst:0xc (SW_CPU)` → **无限重启**。

**原因**：本机是 PARTIAL 渲染（`display_manager.c` pick_render_mode，`buffer_height=12`），
`lv_display_set_matrix_rotation()` 本身就拒绝非 DIRECT/FULL 模式
（`lv_display.c:1128-1140`），matrix 代码根本走不到，却把 draw layer 内存路径打开了。

**修法**：删掉这两行配置（**不要加回来**）；旋转改为「LVGL 只转触摸 +
flush 回调里转像素」，不依赖 matrix。`LV_MEM_SIZE` 20480 → 22528（+2 KiB）给面板留余量。
（「flush 里转像素」这条路后来也被证伪：DMA scratch 拿不到会整机卡死，见事故 5；现由 `bc29851` 的 MADCTL 硬件旋转取代。）

  ```
  W ble_mouse: Pairing failed: 102                          ← ESP_AUTH_SMP_CONN_TOUT
  ```
- 板端 NVS（`nvs_tool.py` 解析 0x9000–0x107000 转储）：`bt_config.conf:bt_cfg_key0` 里**只有 1 个 bond 节**
  `[f4:26:79:df:f1:f0]`；容量配置 `CONFIG_BT_SMP_MAX_BONDS=15`、`CONFIG_BT_BLE_SMP_BOND_NVS_FLASH=y`，
  blob 仅 475 B（上限约 3.9 KB）→ **容量足够放两台主机**，不是"只能存一个"。
- 连接能力：`CONFIG_BT_ACL_CONNECTIONS=4`、`CONFIG_BT_LE_MAX_CONNECTIONS=3`、`CONFIG_BT_MULTI_CONNECTION_ENBALE=y`。
- 根因：**整片 0x0 烧录会覆盖 NVS 分区**（合并镜像在 0x9000–0x107000 之间是 0xFF 填充）→ 板端 bond/CCCD
  被清空，而 Windows 仍保留旧 LTK → 每次连接都在加密阶段失败后断开，形成重连风暴。
  （开机 `CCCD load known=0` 与「烧一次就要重配」的旧现象与此一致。）

### 功耗说明（广播耗电）
- 广播是**周期性短脉冲 TX**，不是持续发射；ESP32-C6 在 100 ms 级广播间隔下平均电流通常在**数百 µA 量级**
  （**理论估算，本轮未实测**）。对比这块 2.16" AMOLED 在 60% 亮度下的背光电流，广播小两到三个数量级，
  **不是主要耗电项**。
- 分级策略的取舍：断开后 30 s 内快广播（30–60 ms）让"回到范围内"的重连仍然 ~1 s 级；之后转慢广播（300–500 ms）
  省电，代价是重连延迟变成约 1–2 s。连接建立后控制器自动停止广播。

### 0.5.5：烧录 WebSocket `1006` 根因与修复（已定因，2026-11-14）

**现象**：0.5.4 下「扫描设备」成功（`GET /airremote/ports` 200，识别 COM3），但点「开始烧录」时
WS 升级失败，页面显示 `code=1006`；同一路由用 Node 直连 `ws://127.0.0.1:9787/airremote/flash`
返回 **101**，host 侧路由本身正常。

**根因（有源码证据，非推测）**：DSH 桌面版的页面是自定义协议页面（`dsh-app:`），
`location.host` 与 `document.baseURI` 都**不是**宿主 HTTP 服务的地址。裸 `new WebSocket(...)`
用它们拼出来的 URL（如 `ws://<页面 host>/airremote/flash`）连不到宿主服务 → 浏览器拿不到握手
→ **1006**。
而 HTTP 的 `fetch('/airremote/ports')` 能成功，是因为同协议下的 HTTP 请求走了桌面壳的协议代理；
**WebSocket 不走该代理**——这正好解释「扫描成功、烧录失败」的分裂现象。

**DSH 的正确做法（`app.asar` 内源码，`@deepseek-ai/dsh-client-connection`）**：
- 桌面壳启动时注入 `globalThis.__DSH_TRANSPORT__ = { ownsHost: true, streamBaseUrl }`，
  `streamBaseUrl` 才是宿主 HTTP 服务的 origin；
- 官方 `openConnectionWebSocket(path, factory, baseUrl)` 的 base 解析是
  `baseUrl ?? document.baseURI`，而 `ctx.connection.openWebSocket(path)` 会传入
  `transport?.streamBaseUrl` 与桌面的**认证 socket 工厂**；
- 因此插件应使用 `ctx.connection.openWebSocket('/airremote/flash')`，而不是自己拼 URL。

**修复（0.5.5）**：
1. client `inject` 增加 `'connection'`，主路径：
   `openFlashSocket = () => ctx.connection.openWebSocket('/airremote/flash')`；
2. 兜底（`ctx.connection` 不可用时）：`__DSH_TRANSPORT__?.streamBaseUrl ?? document.baseURI` +
   `new URL('airremote/flash', base)` + `http→ws`，与官方实现逐字一致；
3. 失败文案带 `code / carrier / base`（不含任何 token）；host 侧在接受升级时记
   `flash socket accepted (origin=…, host=…)`，拒绝时保留 `rejected foreign Origin`；
4. host 的 `/airremote/flash` 协议未改动；`package.json` 的 `dsh.client.inject` 同步加入
   `@deepseek-ai/dsh-client-connection`；版本 0.5.5。

**待真机验收**：用户刷新页面（client JS 需刷新，host 侧 HMR 已生效）后
